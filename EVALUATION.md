# Приёмка и сравнение

## Сквозной сценарий по брифу партнёра

1. Открыть репозиторий в AI IDE, создать рабочую копию: `python scripts/pulse.py init projects/family-live`, положить в неё `sources/` и `data/` из `demo/family-connect`.
2. Запустить агента через `prompts/START.md` с вопросом из брифа. До стратегии агент должен назвать решение, его владельца, сроки двух решений и неизвестные.
3. Проверить, что таблица показателей перенесена без ошибок и что отсутствующие в брифе величины записаны как допущения или неизвестные.
4. Воспроизвести `paid-months` и `sample-size`; сверить с `demo/family-connect/README.md`: итог основного сценария −117 759 руб., 12 720 месяцев для цели, 1 636 групп на вариант.
5. Проверить в `decision.md` пять вариантов, включая «оставить как есть» и «закрыть», и сильное возражение у каждого.
6. Проверить, что агент остановился перед выбором варианта и что статус в `state.json` не «одобрено» без слов человека.
7. Проверить в `strategy.md` пять частей брифа, прогноз по пяти показателям в двух сценариях и разрыв с каждой целью.
8. Открыть новый чат через `prompts/RESUME.md`, дать новый материал и убедиться, что сработало условие пересмотра и появилась запись до/после в `updates/`.
9. Запустить `validate` и `status`.

## Сквозной сценарий по кейсу eSIM

1. Открыть `demo/case` в AI IDE через `prompts/START.md`.
2. Убедиться, что агент формулирует решение, владельца, аудиторию, основную метрику и критерии остановки до стратегии.
3. Воспроизвести команды из `demo/case/README.md`.
4. Проверить `analysis.json`: путь, `n`, единица, период, единица наблюдения, ключ, диапазон и описательная разница. По умолчанию интервалы должны быть `null` с причиной в `uncertainty`.
5. Проверить `economics_analysis.json`: все входы имеют `data_status=synthetic`; для демо `break_even_absolute_uplift=0.03`, при +3 п.п. окупаемость 6 месяцев.
6. В `decision.md` проверить A/B/C, включая статус-кво и закрытие; у каждого должны быть сильное возражение, обратимость, цена и условие выбора.
7. Проверить, что продукт и коммуникация используют один сегмент и одну гипотезу, а план содержит baseline, контроль, знаменатель, MDE, объём/срок, защитные метрики и владельца.
8. Проверить UX-разбор по сохранённому screenshot: утверждения не выходят за видимый материал и одну конфигурацию.
9. Открыть новый чат через `prompts/RESUME.md`; `status` должен показать те же обязательства и триггеры. Добавить новый материал в рабочую копию и проверить до/после без перезаписи истории.
10. Запустить `validate demo/case` и `status demo/case` после обновления.

## Отрицательные и граничные сценарии

Проверять на временной копии/файле, не повреждая демо:

| Сценарий | Ожидание |
|---|---|
| Битая внутренняя ссылка или локальный источник evidence | `validate` → код 1 и конкретный путь |
| Дублированный evidence ID | `validate` → код 1 и ID |
| Ссылка решения на неизвестный evidence ID | `validate` → код 1 |
| Обязательство без владельца, срока или ожидаемого результата | `validate` → код 1 |
| Просроченное открытое обязательство | `status` показывает `ПРОСРОЧЕНО` и итоговое число |
| Дубль `(key, group)` в `analyze --key ...` | `analyze` → код 2, строка не считается дважды |
| Метрика вне `--min-value/--max-value` | `analyze` → код 2 |
| Одно наблюдение на группу | корректный JSON, `stdev`/интервал `null`, без ошибки NaN |
| Пустая/нечисловая метрика | исключение подсчитано и показано в warnings |
| `--normal-approximation` при n<2 | нет интервала, есть предупреждение |
| Отрицательная маржа/трафик или NaN в economics | `economics` → код 2 |
| Повторный `init` | существующие файлы не перезаписаны |
| `sample-size` с одинаковыми `--p1` и `--p2` или долей вне (0, 1) | `sample-size` → код 2 |
| `paid-months` с отрицательным числом номеров, оттоком больше 1 или месяцем вне года | `paid-months` → код 2 |
| `paid-months` без сценариев или с отсутствующим файлом | `paid-months` → код 2 и путь |

## Минимальные критерии качества

| Область | Проверяемый результат |
|---|---|
| Проверяемость | каждое существенное утверждение связано с evidence ID и источником/ограничением |
| Релевантность | источник способен изменить выбор; нерелевантные материалы отмечены withdrawn/context |
| Разнообразие решений | ≥3 содержательно разных варианта, включая бездействие и закрытие |
| Аналитика | формула/скрипт, единицы, период, пропуски, ключ наблюдения и честная неопределённость |
| UX | URL, дата, viewport/состояние, видимое наблюдение и граница вывода |
| Экономика | маржа отделена от выручки; полная стоимость, диапазоны, чувствительность и окупаемость воспроизводимы |
| Честность | синтетические данные и прогнозы не выданы за факты; одобрение человека не симулируется |
| Сопровождение | state/decision/ledger/updates согласованы; обязательства имеют владельца, срок и результат |
| Экономичность | модель, поиск, повторы и минуты человека записаны либо явно названы неизмеренными |
| Переносимость | запуск из чистой копии по README без скрытых ключей |

## Baseline для защиты

Сравнивайте один и тот же brief и набор материалов:

- **Обычный чат:** тот же модельный тариф и доступ к источникам, но без обязательного журнала, вариантов, состояния и скриптов.
- **Ручной аналитик:** время до первой проверяемой рекомендации, число ручных шагов и проверок.
- **Пульс:** время до evidence map и рекомендации, доля релевантных утверждений с источником, найденные неизвестные/противоречия, полнота обязательств, стоимость LLM + поиск + повторы + минуты человека.

Для 3–5 одинаковых задач сохраняйте исходные brief, полные ответы, модель/тариф, счёт или токены, время, повторы и ручные исправления. Без этих артефактов сравнение является наблюдением, а не воспроизводимым преимуществом. Исторические ограничения — `evaluation/results.md`.
